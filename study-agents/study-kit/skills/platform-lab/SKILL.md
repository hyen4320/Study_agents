# 플랫폼 · 기술 구축 학습

## 핵심 원칙

**세우는 것은 절반이고, 고장내고 복구해야 아는 것이다.** 튜토리얼을 따라 치는 것은 학습이 아니다.

## 응답 원칙

- **두괄식.** "결론: 이 기술은 ~문제를 ~로 해결하며, 최소 구성은 ~입니다."
- 존댓말.
- **공식문서가 정본이다.** 기억으로 명령어를 쓰지 않는다. `source-scout` 에이전트로 먼저 문서를 확인한다.
- 버전을 항상 명시한다. 버전 없이 쓴 명령은 틀린 명령이 된다.

## 6단계 루프

### 1단계 — 왜 이 기술인가

세우기 전에 묻고 답한다:

- 이 기술이 없으면 무엇을 손으로 해야 하는가
- **대안은 무엇이고 왜 이것을 고르는가** (대안 2개는 이름과 차이를 댈 수 있어야 한다)
- 쓰지 말아야 할 규모·상황은 언제인가

### 2단계 — 공식문서 확보 (추측 금지)

`source-scout` 에이전트를 띄운다. 받아야 할 것:

| 항목 | 왜 |
| --- | --- |
| 정본 문서 URL | 블로그 따라 하면 버전이 어긋난다 |
| 현재 안정 버전 | |
| 최소 사양·선행 조건 | 사양 미달이면 중간에 깨진다 |
| 아키텍처 구성요소 | 무엇이 무엇과 통신하는지 |
| 공식 Quick Start 경로 | |

**읽기 전에 설치하지 않는다.**

### 3단계 — 개념 지도 먼저

명령을 치기 전에 **구성요소와 데이터 흐름을 그린다.** 사용자에게 그려보게 하고 틀린 곳을 고쳐준다.

최소한 이 질문에 답할 수 있어야 다음으로 간다:
- 요청이 들어오면 어떤 순서로 어디를 지나는가
- 상태(state)는 어디에 저장되는가
- 재시작하면 무엇이 사라지고 무엇이 남는가
- 인증은 어떤 방식인가

### 4단계 — 최소 구성으로 세우기

**풀 구성을 피한다.** 동작하는 가장 작은 단위부터.

진행하며 반드시 기록한다:

```
study/platform/<기술>/구축기록.md

| # | 실행한 명령 | 결과 | 막힌 점 | 해결 |
```

**에러를 지우지 말고 전부 남긴다.** 에러 로그가 이 학습의 주된 자산이다.

환경 전제도 적는다 — OS, 버전, 메모리, 네트워크 제약(사내망 차단 여부 등).

### 5단계 — 일부러 고장내기 (이 단계를 생략하지 않는다)

세워졌으면 **최소 3가지를 망가뜨리고 로그만 보고 원인을 찾게 한다.**

| 고장 유형 | 예 |
| --- | --- |
| 설정 오류 | 포트·엔드포인트·경로를 틀리게 |
| 인증 실패 | 자격증명을 만료·오타 |
| 자원 부족 | 메모리·디스크 한계 |
| 네트워크 단절 | 구성요소 간 통신 차단 |
| 상태 손상 | 프로세스 강제 종료 후 재시작 |

각각에 대해 기록한다: **증상 → 어느 로그에 무엇이 찍혔나 → 원인 → 복구 방법.**

이 표가 실무에서 쓰이는 유일한 부분이다.

### 6단계 — 자동화·정리

- 세운 과정을 **재현 가능한 스크립트/IaC로** 다시 쓴다. 손으로 두 번 하지 않는다
- 자원을 정리한다 (클라우드면 과금 확인)
- **정리 전에 증빙 캡처·로그를 먼저 확보한다**

## 세션 종료

`study/platform/<기술>.md` 갱신. 다음 절을 반드시 채운다:

- **함정** — 문서에 있지만 놓치기 쉬웠던 것
- **고장·복구 표** — 5단계 결과
- **환경 전제** — 이 기록이 유효한 조건
- **미해결** — 못 한 것, 막힌 것을 솔직히

## 금지

- 공식문서 확인 없이 기억으로 명령어 제시
- 버전 표기 없는 설치 안내
- 고장내기 단계 생략
- 에러 로그를 "해결됐으니" 지우기
- 처음부터 프로덕션급 풀 구성 시도
- 사용자가 실행할 수 없는 환경(사양·네트워크 미확인)에서 절차부터 진행
